# DroidDS 0.0.2 CPU probe: owner-supplied Thor result

<!-- CodexAstraUlt: Record the first owner-supplied Android execution result
without publishing private run identifiers or promoting fixture checks to game,
graphics, performance or independently verified package evidence. -->

The owner ran DroidDS Probe 0.0.2 on their AYN Thor and supplied its
`latest-probe.json` after the app reported a pass. The existing
`tools/run_android_probe.py::validate_report` accepts the uploaded report: all
four CPU cases have the required exact results and route counters, and both
intentional corruption controls report the expected rejection. The raw report
remains outside the repository; this record omits run identifiers, process ID
and device timestamps.

The report identifies an Android `aarch64` process with 64-bit pointers and an
observed host page size of **4,096 bytes**, using ABI 4 / generation 3 and app
version 0.0.2 / code 2. The device model is supplied by the owner rather than
recorded in this JSON. This is the first reported device execution of this CPU
slice; it is not a cloud-host or cross-compilation result.

| Original fixture | Native calls | Native instruction budget charged | Fallback steps | Native lookup hits | Comparison interpreter steps | Result |

| `arm_integer_memory` | 1 | 11 | 0 | 0 | 11 | Passed |
| `thumb_integer_memory` | 1 | 7 | 0 | 0 | 7 | Passed |
| `arm_missing_entry_fallback` | 1 | 2 | 3 | 0 | 5 | Passed |
| `arm_to_thumb_native` | 1 | 5 | 0 | 1 | 5 | Passed |

Each case reports checkpoint SVC 42, zero instruction callbacks and a comparison
of 65,536 memory bytes. The strict expected-output comparison, strict interpreter
comparison and exact route-counter comparison all pass. In particular, the
missing-entry case exercises three interpreter fallback steps, and the native
ARM-to-Thumb case records one native lookup hit.

Both negative controls pass by rejecting intentionally different integer data:

- `nan_shaped_integer_register_mismatch`: rejects the difference in register r6.
- `nan_shaped_integer_memory_mismatch`: rejects the difference at memory byte
  `0x00004004`.

These controls exercise strict integer/memory comparisons even when the bit
patterns resemble floating-point NaNs. They do not test VFP arithmetic.

## Validation boundary

<!-- CodexAstraUlt: Reusing the uploaded nonce proves internal consistency only;
do not give a manually exported JSON the stronger provenance of a fresh ADB run. -->

The validation used the known 0.0.2 version fields and the request identifier
already in the uploaded report. That checks report structure, declared platform,
version agreement, route counts, results and negative controls. It does **not**
bind this upload to a freshly issued host request or to a hash of the installed
APK. The report contains no APK digest, signing certificate, source commit,
device model, Android build, GPU or driver metadata. Its app version fields are
self-reported; they are not an independently decoded installed manifest.

To reproduce this consistency check with a private copy outside the checkout:

```bash
PROBE_REPORT=/absolute/private/path/droidds-latest-probe.json python3 - <<'PY'
import json
import os
import sys
from pathlib import Path

sys.path.insert(0, "tools")
from run_android_probe import validate_report

report = json.loads(Path(os.environ["PROBE_REPORT"]).read_text())
validate_report(report, report["android_shell"]["request_id"],
                {"version_code": 2, "version_name": "0.0.2"})
print("Uploaded 0.0.2 report is internally consistent and passes CPU gates")
PY
```

Run that command with the 0.0.2 validator from tag `v0.0.2-probe.2`; a future
validator may require additional fields. The existing ADB runner provides the
stronger fresh-request and installed-APK-hash checks when a local device operator
uses it for a new run.

The shell timestamps differ by 12 ms. This is a single device wall-clock interval
for tiny diagnostic fixtures, with no verified clock, repeat-run distribution,
thermal information or gameplay workload. It supports no emulation-speed,
latency or sustained-performance claim. A 4 KiB-page run does not qualify a
16 KiB-page device. Broader CPU semantics, code/module lifetime, Android
lifecycle, Vulkan rendering, memory stability and games remain untested by this
report.
