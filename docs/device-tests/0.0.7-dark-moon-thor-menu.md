# Dark Moon: first interactive menus on Thor

Reported **2026-11-03** (America/New_York). The owner supplied two successive
local-session summaries. The first completed all **521 Android objects** and a
private APK, preserving the original game, Linux artifacts and earlier reports.
ADB access was initially blocked. The subsequent authorized device run reached
Dark Moon's title and file-selection menus on the Thor in **Native** mode; the

This achieves the central **0.0.7 first owned-game boot objective**. Development

## Audio observation

<!-- CodexAstraUlt: Retain the measured count and the owner's audible/visible
observation without converting cumulative underruns into a speed estimate. -->
The device summary reports **1,361 audio underruns**. The owner subsequently
described crackling, visibly slow frame progression and audio switching on/off
roughly with each frame during another observation. This is consistent with
slow guest sample production, but a count without timing and PCM delivery data
does not quantify emulation speed or establish a single cause.

The owner subsequently supplied both exported reports. They have matching input,
title-manifest and compiled-library identities, report Native CPU execution and
Vulkan rasterization on Adreno 740 at **1×**, and stop normally. Neither report
contains an installed APK version or end-to-end active wall duration.

Guest time uses the runtime's 268,111,856 cycles/second. Core time excludes
Java/audio/pacing overhead and paused idle, so the percentages are **upper bounds
on whole-session active emulation speed**, not measured end-to-end speed or game
FPS. Different run lengths, phases and pause counts do not establish a
regression between the tests. A high native instruction share also does not
measure the fraction of host time spent interpreting or shading.

The audio output received every converted sample while the core produced only
about 21 seconds of PCM in 100 seconds, then 34 seconds in 202 seconds. This
establishes substantial slow sample production. The independently reproduced
queue-overflow defect is **not evidenced in these two reports**, which show zero
drops. Teardown timing also cannot explain the measured core slowdown. Retain
the original underrun counts; do not relabel them as harmless lifecycle noise.

Both reports show zero runtime faults, unsupported services/SVCs, memory-fault
pages, GPU draw errors, compiler failures, resource-limit events and software
raster fallbacks. The 64 MiB application-memory counter is guest memory, not
whole-process or driver memory. These final counters cannot qualify leak freedom
or visual correctness.

CPU vertex shading is selected in both reports. Reported `vertices_drawn` totals
are 439,291,962 and 924,201,498; source inspection shows this counter largely
counts submitted array/index entries, including duplicates and some rejected
draws. It is **not** a count of actual shader invocations. The second run's much
larger dispatch count and the CPU vertex path are profiling leads; the old
reports do not isolate their cost from command processing or screen readback.
