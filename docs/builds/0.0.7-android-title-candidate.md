## Implemented path

<!-- CodexAstraUlt: Describe concrete integration responsibilities and the
limitations that matter when deciding whether this can launch a private title. -->
- `droidds-title-runtime` admits a matching input and installer-owned library,
  verifies full byte/component/layout/origin identities, then owns the live
  loader/HLE/PICA machine. Native base code is immutable; CROs stay interpreted.
  Android 4 KiB pages now support the existing fence; other native page sizes
  reject. Interpreter remains an explicit diagnostic choice.
- Execution yields between bounded slices without treating a slow startup as
  a fatal frame timeout. A slice delivers only completed guest frames and
  drains PCM independently. Wall limits are cooperative: they cannot preempt
  a single long core/GPU call.
- `droidds-title-player` and JNI implement thread-owned sessions, fixed transfer
  capacities, lifecycle operations and bounded reports. Kotlin/Gradle or a
  desktop frontend are not introduced.
- The Android frontend imports through the system picker with streaming size
  and SHA-256 checks, cancellation and atomic publication. Runtime data lives
  separately and survives stop/reopen. Controls include buttons, both sticks
  and lower-view touch. Pause/resume tickets prevent duplicate execution loops;
  a lifecycle epoch also handles transitions completed before the worker sees
  them. New sessions hide old images until their own frames arrive.
- The separate compiler consumes retained prepared C, producing resumable
  ARM64/Bionic objects with the pinned NDK. The packager binds one title,
  three native libraries, Java frontend, notices and a small manifest. Private
  inputs remain outside the APK and are imported separately. Owner profiles
  preserve signing identity; public original candidates use a diagnostic key.

Both guest screens still share one physical Android display. Vulkan rasterizes
PICA output; CPU readback and Bitmap/Canvas present it. No direct presentation,
physical dual-display support, general native mutable code, encrypted import,
or private-game performance is established by this candidate.

## Native qualification and scheduler cost

<!-- CodexAstraUlt: Optimize the measured scheduling cost without restoring
the old missed-deadline behavior or misrepresenting a microbenchmark as gameplay. -->
Raw checkpoint reports now include cumulative native/interpreter/callback work.
A matching point cannot qualify native execution performed only later. Typed,
monotonic timeline validation rejects inconsistent work accounting; raw state
differences are retained separately from synchronized observations.

An earliest-timer prepass avoids repeated nested waiter scans in common cases,
without adding a cache or weakening deadlines. Four new tests include an
independent oracle across 256 mixed states, ordering, ties and mutations.
For 200,000 original interpreted spin instructions with 64 waited timers,
median host time drops from **376.290 ms at 857ff47 to 20.540 ms**, or 20.688 ms
with reversed timer order. Five measured samples follow a warm-up on a shared
cloud host. The older b61a986 takes 2.605 ms but misses the corrected deadline
checks. Remaining overhead and the unwaited-minimum nested fallback remain;
these numbers establish neither Dark Moon speed nor handheld performance.
Reproduce with the original `zakuro-core` `scheduler_cost` example.
