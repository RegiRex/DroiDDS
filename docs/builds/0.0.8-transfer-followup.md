## Candidate scope and coherence requirements

<!-- CodexAstraUlt: Defer work only when a tiled intermediate has no immediate
linear presentation requirement; preserve consumers, CPU visibility and bounds. -->
The candidate changes the accepted **hardware tiled-output display-transfer**
path. It is intended to leave the result on the GPU, deferring host capture,
screen/presentation preparation and submission until a consumer or normal
flush boundary needs them. Recorded transfer computation, twins, dirty ranges,
CPU-write guards and overlap reconciliation remain required. It does not skip
transfers, shader calculations or draws.

Transfer-only streams are bounded to **32 deferred tiled transfers per batch**;
reaching that bound submits the recorded work. Actual submissions for other
reasons also reset the deferred count. A consumer may force earlier submission
or readback. The bound is a command-count limit, not a whole-renderer byte limit
or an assertion that every 32 requests become one submission.

The old submission boundary also cleared each surface's `checked` flag. The
candidate preserves that reset at every deferred tiled-transfer boundary so
that later requests revalidate CPU memory, including clean or unguarded source
memory written between transfers. This is **surface-validation state**, not a
change to Vulkan command-buffer reset checking. Existing sync/writeback must
still obtain current guest-visible bytes when a CPU consumer requires them.

**Linear-output transfers retain their previous eager path**, including capture,
screen preparation, submission and `ScreenRef` batch/history behavior. A tiled
intermediate cannot be treated as a linear screen framebuffer. Software fallback,
overlap and unsupported-transfer behavior remain part of correctness validation.

<!-- CodexAstraUlt: Separate cache idleness from real GPU fence lifetime so
batching cannot silently extend the prior cache eviction horizon. -->
The candidate also separates the cache's logical activity clock (`cache_epoch`
and `idle_used`) from the actual submission `batch`. Fewer physical submissions
must not multiply logical idle age by the new batch size. Reclamation is checked
at actual submissions, so a sweep can wait up to one bounded transfer batch;
unfinished GPU references still prevent destruction. Actual `used` batch stamps
and completed fences remain responsible for resource lifetime. Selected images
are restamped after depth-sample allocation because it can rotate the command
batch while earlier views remain bound to the draw. This separation is a
retention safeguard for the new batching policy, not proof that the previous run
leaked memory or that all renderer memory is now bounded. Cache eviction/coherence
tests remain required.

**Texture-copy behavior remains unchanged.** Its source/destination synchronization
and existing CPU byte-copy ordering provide immediate guest-byte visibility.
The candidate measures those phases rather than extending display-transfer
deferral to a distinct operation with different visibility requirements. Stride,
overlap, empty requests and existing short-tail behavior must remain unchanged.

Preparation, generated-title ABI, both completed 521-object private target
builds/libraries, imports, saves and owner signing identity remain reusable.
Only the generic player is rebuilt during repackaging. Native guest execution,
CPU vertex shaders and Vulkan 1× remain the private test priority; further Thor
GPU tests and audio-perfection work stay deferred. The optional shader JIT remains
disabled.

## Fixed route and phase diagnostics

<!-- CodexAstraUlt: Keep route acceptance and nested wall-time phases explicit;
new measurements must not create unbounded traces or double-count their parents. -->
The candidate exports fixed `runtime.gpu.transfer_processing.display` and
`.texture` records. They are nested inside the existing GSP/SVC timing scopes;
do not add them to those parent durations or to total core time.

| Record | Intended fields and scope |
| --- | --- |
| Display request total | Calls and whole-request wall time, including empty/software paths. |
| Display hardware route | Attempts, accepted requests, fallbacks, errors, accepted tiled/linear counts and hardware wall time. Errors are a subset of fallbacks, not an extra partition. |
| Display software route | Calls/empty requests, input sync, output sync and copy/conversion wall time. Copy time includes allocation, memory reads, conversion and writes. |
| Texture copy | Calls, contiguous/strided route counts, total wall time and disjoint input sync, output sync and byte-copy phases. |
| Hardware deferred work | `deferred_tiled_transfers` and `deferred_transfer_flushes`, alongside existing actual submissions and retained-surface count. |

Hardware time includes its reconciliation, command recording, captures and any
submission waits; the candidate does not claim to split every internal hardware
wait. Software synchronization can include GPU readback. The display hardware
attempt duration and software phase durations are subsets of that request's
total, while texture phases partition portions of their own total. Branch
overhead may remain outside the recorded phases. Calls use fixed accumulators
at natural request boundaries; no per-pixel timers, address histories, shader
dumps or growing trace are introduced.

Lazy execution can move cost into a later sync, command, scanout or flush scope.
**A smaller display-transfer timer alone is not an end-to-end improvement.**
The next report must retain total worker/core time, guest work counts, actual
route counts, submissions and errors. Paired authored benchmarks must include
the required final consumer/readback/flush, not time only command recording.
Code 16 supplies no tiled/linear acceptance ratio, so the share of its workload
eligible for this change remains unmeasured.
