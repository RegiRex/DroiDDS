## Concrete audio corrections

<!-- CodexAstraUlt: Preserve exact PCM and truthful counters while fixing an
independently reproduced queue error and a shutdown measurement boundary. -->
The title output queue previously enqueued a new PCM chunk before draining old
samples, discarding data even when the platform had space available. The corrected
queue drains existing samples first and preserves ordered PCM through bounded
partial/zero writes. An original 4,096/4,096/3,000 guest-frame input sequence
loses 3,421 output frames with the previous order and zero with the correction.
The same ordered PCM is retained. Genuine overload remains visible as drops.
The queue stays at 8,192 stereo frames with nonblocking writes; there is no
filler audio, time stretching, larger buffer or extra audio thread.

Audio now stops before native report collection and GPU/resource destruction.
Previously, an empty AudioTrack could continue accumulating underruns during
teardown. Cleanup attempts each platform operation once, retains the first
error and cannot prevent native cleanup. The unused per-slice playback-head
query is removed. Partial/zero write counts and the queue high-water mark are
retained as fixed aggregates.

These are real corrections, but neither explains the reports' core slowdown;
the queue-loss defect is not observed in their zero-drop counters. A brief
UI-stop-to-worker-return interval can still contribute audio underruns, and old
reports cannot tell how many occurred in it.

## Bounded timing and identity

<!-- CodexAstraUlt: Export fixed aggregates instead of expanding logs or adding
sampling workers. Keep timing scopes and denominators explicit for comparison. -->
The report now includes installed package/version metadata, queried once, and:

- `timing.worker_run_wall_ns`: worker-running intervals, including an in-flight
  call after a UI pause/stop request; excludes initial open, paused idle and
  final native teardown. This is the denominator matched to total guest cycles.
- `timing.active_wall_ns`: UI foreground/unpaused intervals. It can end before
  an in-flight native call, so do not use it with the full guest-cycle count.
- Native/JNI and audio-submit total/max times, completed-frame work, requested
  pacing delay, scheduler lateness and maximum active gap between nonempty PCM
  submissions. These are producer-delivery observations, not audio-device clocks.
- `runtime.scanout`: attempts and total/max host time reading both screen planes,
  including synchronization and pixel conversion. Only completed guest frames
  attempt scanout, and no frame is skipped by this instrumentation.
- `runtime.gpu.command_processing_wall_nanoseconds`: the already-existing
  command-list timer. It includes decoding, CPU vertex/geometry processing,
  command recording and waits, but excludes standalone transfers/fills and
  screen readback. It is not GPU utilization or hardware execution time.

Scanout and command-processing time measure disjoint host-call phases inside
core slice time. Asynchronous GPU work may span phases; their difference from
core time still includes other service, CPU, transfer and synchronization work.
There are no per-frame log records, growing histories, sampling timers or threads.
Scanout adds two monotonic clock reads per completed frame. The shader/compiler
settings, generated game C, native ABI and ten retained compilation helpers are
unchanged.

## Architectural next decision

<!-- CodexAstraUlt: Distinguish guest ARM recompilation from PICA vertex shading
and let measured host costs select a controlled optimization experiment. -->
The integrated-GPU heuristic currently selects CPU vertex shading on the Thor.
That uses batched PICA interpretation because the optional CPU shader JIT is
disabled; recompiling guest ARM code does not make PICA shaders native. The
heuristic does not inspect JIT availability. This is a candidate cost, not proof
that forcing GPU vertex shaders or enabling the existing JIT improves Dark Moon.
The reported vertex counter counts submitted references, not unique shader work.

Use the next matched report to choose the next experiment:

| Dominant measured cost | Next focus |
| --- | --- |
| Command processing | Isolate CPU vertex processing and draw/command overhead; compare CPU/GPU alternatives using original correctness fixtures before a device A/B. |
| Scanout | Investigate synchronous readback, image conversion and presentation while preserving every required draw and both screens. |
| Other core work | Inspect guest dispatch, services, transfers and module/interpreter work; instruction share alone is not host-time share. |
| Frontend or callback delay | Investigate measured Java/audio work and scheduling delays separately from the guest core. |

Do not enable the existing unbounded shader-JIT worker path wholesale or change
renderer routes merely to reduce an underrun counter. A matched private test
still determines audible quality, rendering correctness and actual speed.
