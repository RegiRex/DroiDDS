# 0.0.7 preparation: initialize shared-page readiness

<!-- CodexAstraUlt: Record the generic startup correction and its independent
regression separately from the still-unverified private-title causal link. -->
The owner's [run-004 trace](../host-tests/dark-moon-2026-10-22.md#owner-reported-run-004-scheduler-trace)
shows Dark Moon repeatedly sleeping for one millisecond, waking on its deadline,
then sleeping again 13 cycles later. The owner subsequently supplied event #3:
R4 is `536350720` (`0x1FF81000`), the shared-page base. This supports the
shared-page polling lead; the intervening load and its offset remain unobserved.
The readiness byte below lies at R4 + `0x86`, but the pointer alone cannot prove
that Dark Moon reads it.

Source inspection found an initialization omission: `init_shared_page` cleared
the page but never initialized offset `0x86` (guest address `0x1FF81086`). The
Azahar-family shared-page reference initializes this byte to one for startup
readers that wait before querying `running_hw`. DroidDS now writes that value
after initializing the page. This is an independently implemented interface
correction; no source from the reference implementation was imported.

The runtime change is one byte write per page initialization. It adds no loop,
timer, dependency or ongoing diagnostic work. Clock-slot publication, syscall
responses, scheduler behavior and rendering are unchanged. No game identity or
instruction address selects the fix. The existing optional scheduler trace is
retained, and reports now also hash the shared-page source file.

## Regression evidence

<!-- CodexAstraUlt: Validate observable guest behavior with original code and
a failure control, rather than testing only a literal initializer assignment. -->
An independently authored ARM program in an original NCCH fixture reads the
readiness byte, sleeps while it is zero, checks the running hardware byte, then
exits. The production loader, read-only shared-page mapping and interpreter are
used on both Old and New 3DS models:

- A fresh loaded guest reaches its exit checkpoint without sleeping.
- Clearing only readiness recreates repeated sleeps under a ten-millisecond
  emulated bound without exit or a memory fault.
- Restoring readiness releases that same waiting guest and reaches its exit.
- Clock and slider updates preserve readiness and the adjacent hardware/battery
  state across 120 updates on both models.

Before the production correction, the new integration test failed because the
mapped readiness byte was zero. It passes with the correction and is required
by the runtime build gate. An independent source review verified the original
fixture's literal loads, branches, controls and the one-byte production scope.
