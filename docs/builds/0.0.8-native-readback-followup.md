## Implemented consumer-specific capture policy

<!-- CodexAstraUlt: Match work to the actual title frontend consumer without
removing native-memory coherence or changing other renderer clients globally. -->
The title frontend consumes native-resolution bytes through
`System::read_screen`. The candidate introduces an immutable per-instance
**NativeReadback** mode for that consumer. For accepted **linear** hardware
display transfers, it omits otherwise unused upright/screen presentation
captures while retaining native capture, synchronization and submission.
This targets a path actually observed in code 17.

The mode is an internal runtime choice, not a new user-facing rendering option
or a process-wide environment toggle. The existing default scaled/direct
consumers retain their current captures and presentation/history behavior.
The change does not remove draw calls, discard pixels, relax guest-byte
visibility, bypass texture-copy synchronization or reuse stale images.
CPU vertex shader policy and the optional shader-JIT setting remain unchanged.

Executed authored controls establish exact native-byte output and avoided
capture work separately, including CPU reads/writes, dirty ranges, aliases,
formats, fills, transfer chains, failure behavior and retained twin/scaled
consumer behavior. Default-mode controls preserve screen history and the direct
presentation contract. The paired benchmark includes eventual consumers,
synchronization and readback. These local controls do not establish faster
end-to-end operation on the Thor.

## Fixed attribution and architecture scope

<!-- CodexAstraUlt: Attribute the remaining active work without growing traces
or confusing the native Android package with removal of emulated graphics. -->
Fixed metrics pass the source-bound authored runtime checks.
`runtime.gpu.hardware.framebuffer_presentation` identifies the immutable
consumer mode. `native_captures`, `screen_captures`, `upright_image_captures` and
`skipped_screen_captures` count recorded or intentionally omitted capture work,
not completed GPU operations or skipped guest draws.

`runtime.gpu.hardware.transfer_work` contains five disjoint display-phase subsets
of the existing hardware-attempt wall timer:

- `reconciliation_wall_nanoseconds`
- `transfer_recording_wall_nanoseconds`
- `native_capture_wall_nanoseconds`
- `presentation_capture_wall_nanoseconds`
- `submission_wall_nanoseconds`

It also retains `readback_wait_wall_nanoseconds`,
`readback_store_wall_nanoseconds`, `readback_wait_calls` and
`readback_store_calls` across contexts. These can nest inside display phases or
command processing and must not be added to their parents. A wait count means
a completion-check/wait request, which can return immediately; neither that
count nor elapsed wall time measures pure GPU blocking time. Branch overhead
can remain outside the five display phases.

The executed authored runtime image/PCM oracle observes `native_readback`, with
positive native captures equal to accepted linear transfers and skipped screen
captures, while screen/upright capture counts and presentation-capture wall time
remain zero. Exact image/PCM checks and the separate default scaled/direct
consumer controls pass.
The aggregates use fixed storage at operation boundaries, without per-pixel
histories or continuously growing diagnostic logs.

DroiDDS already produces per-title ARM64 APKs using the existing AOT compiler
and retained runtime. Code 17 records **99.989957% of counted guest instructions
on its native route**, but that fraction is not elapsed time. Disjoint command,
display-transfer, texture-copy and scanout scopes account for **93.32% of core
time**. Changing packaging or native dispatch alone does not address those
measured graphics scopes.

The [native Android direction](../NATIVE_ANDROID_DIRECTION.md) stages GPU
resource ownership and native graphics/presentation work with separate
correctness and whole-workload performance gates. The readback candidate is a
bounded first step, not a claim of full graphics replacement or playable speed.
Retain the current accurate fallback and per-title AOT path while evaluating
those stages. This candidate does not require regenerating the private prepared
title or recompiling either retained 521-object title library; keep the
generated-title ABI, signing identity, imports and saves compatible.
