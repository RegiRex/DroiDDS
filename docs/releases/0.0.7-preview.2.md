# DroiDDS 0.0.7 preview 2 — generic Android title player

<!-- CodexAstraUlt: Describe the new application path separately from its still
unperformed handheld and owned-game qualification gates. -->
Preview 1 was held by a test race while Linux reaped an already-terminated child.
Preview 2 corrects that test observation and improves CI failure reporting;
production process limits remain unchanged.

This candidate brings the generic title runtime onto Android: a matching input
is imported and verified, one ARM64 title library runs through the shared
loader/services/graphics/audio path, and the app keeps durable runtime storage
across stop/restart. Startup yields between bounded slices so a slow title can
continue progressing without an invented frame or a fatal per-frame budget.

The public download includes only DroiDDS's authored interactive test title.
It exercises the new generic path rather than the previous fixture-specific
probe session. It does **not run Dark Moon or other retail games**. Those need
their own private preparation, Android library and matching input. The earlier
Linux title library cannot execute on the Thor.

Host gates cover original native/interpreter execution, exact screen and audio
output, Vulkan rendering, input, import cancellation, file preservation and
session ownership. The APK must also pass actual ARM64 compilation, manifest,
library, signature and package audits before publication. These checks do not
establish Android execution, retail save compatibility or handheld performance.

<!-- CodexAstraUlt: Give a short device gate for the real included original;
no retail data, new laptop installation or unrelated cleanup is needed. -->
Install `DroiDDS-0.0.7-preview.2-original-android-arm64.apk` and open **DroiDDS**.
It has a separate application identity from **DroidDS Probe**.

1. Tap **Load included test**, keep **Native**, then tap **Play**.
2. Check both guest images, the moving marker, D-pad/A and touch inside the
   lower guest image. Listen for the steady tone.
3. Pause/resume, briefly switch apps and return, then stop. Start again and
   confirm the included input is retained.
4. Export the title report and share it with any visible or audible issue.
   A short **Interpreter** comparison is useful if Native fails.

Both guest views use **one physical display**. The Thor's separate lower screen
is not supported in this candidate. Presentation still uses screen readback and
Bitmap/Canvas. Native admission currently requires 4 KiB host pages; 16 KiB
library alignment alone does not qualify native execution on 16 KiB devices.

This preview advances the Android application and integration work. Roadmap
**0.0.7's owned-game boot gate remains open**, as do gameplay/save qualification,
sustained memory/performance testing and the **0.1.0 beta** acceptance gates.
Device execution of this particular APK is pending when it is first published.

<!-- CodexAstraUlt: Explain the disposable public signer without suggesting
uninstalling an owner's private title app or deleting unexported data. -->
Public original candidates use an ephemeral diagnostic signing certificate.
Future candidates may require a separate manual reinstall; export any wanted
report first. Private per-title builds use an explicit owner signing profile
so updates can retain their application data. No signing key or profile is
included in the release.

The four assets are the APK, `BUILD_REPORT.json`, `SHA256SUMS` and
`THIRD_PARTY_NOTICES.txt`. The build report contains public artifact identities
and producer provenance, with local command lines, paths and private profiles
excluded.

<!-- CodexAstraUlt: A local four-asset bundle cannot label an uncommitted build
as if it came from the public tag. The APK report and checkout must agree. -->
Release preparation requires a clean committed checkout whose HEAD equals the
requested source commit. The packager's complete source inventory must still
match that checkout. Build and bundle directories stay outside Git; changing a
tracked build input requires a new package build before publication. The publish
job repeats artifact, source, signature and uploaded-byte checks before making
its draft public.
